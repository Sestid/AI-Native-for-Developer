## 2. 架构红线（Architecture Guardrails）

红线是「绝对不能跨越」的边界。AI 触碰红线时必须停下并向人确认。

1. **依赖单向**：上层可依赖下层，下层禁止反向依赖上层。
2. **分层不跨级**：每一层只与相邻层交互，禁止越层直接调用。
3. **职责单一**：一个文件 / 模块只做一件事，不混合不同关注点。
4. **禁止循环依赖**：模块 A 依赖 B 时，B 不得直接或间接依赖 A。
5. **副作用归位**：网络请求、全局状态写入、用户提示等副作用只能出现在约定的层。
6. **公共抽象慎改**：触碰共享 / 公共组件 / 路由 / 拦截器属于高风险改动，必须先出 Plan。

> 具体到某语言 / 框架的红线，写进 `conventions.md`，本文件只放与技术无关的通用原则。

## 3. 改动级别约定（Change Levels）

每次任务开工前，AI 必须先声明改动级别：

| 级别 | 含义 | AI 授权 | 典型场景 |
|------|------|---------|----------|
| **L1 隔离新增** | 仅新增文件，不改老代码 | 自由发挥 | 新增功能 / 组件 / 工具函数 |
| **L2 局部增强** | 改 1-3 个老文件，不动公共抽象 | 先列清单，确认后动手 | 给老模块加字段 / 加能力 |
| **L3 跨模块改造** | 涉及公共 / 共享 / 路由 / 配置 | 必须出 Plan，分 PR | 改基础设施、改公共组件 |

**配套规则**：写完后 AI 必须把「实际触碰文件清单」与事前声明对账，多一个少一个都要解释。

## 4. 红线行为清单（DON'T）

AI 自查时照着对：

- ❌ 越层调用（跳过中间层直接访问底层）
- ❌ 跨模块互相 import 内部状态 → 应提到共享层或重新设计
- ❌ 把临时 / 局部状态塞进全局状态
- ❌ 顺手重构无关代码（重命名、抽函数、改格式）→ 必须被 guard 拦住
- ❌ 在纯函数 / 领域层里调用 API 或触发副作用
- ❌ 凭空编造内部接口约定 / 业务规则 → 这些只能来自人给的上下文
- ❌ 用「大概」「可能」糊弄不确定项 → 应停下来要澄清
