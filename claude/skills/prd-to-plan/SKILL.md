# PRD → 结构化开发文档

> 一句话定位：动手前先把需求抽干净，Plan 没说清的代码就一定写不对。

---

## 触发时机（When to use）

- 拿到一份 PRD / 需求说明 / 设计稿，准备开发新功能时。
- **不要用于**：已经有清晰 Plan 的小改动、纯 bug 修复。

---

## 输入（Input）

- 产品 PRD 或需求描述（粘贴原文）。
- 项目宪法：`memory/project.md`、`memory/conventions.md`。

---

## 流程（Steps）

1. **抽功能边界**：列「必须实现的核心能力」与「明确不做的能力」，各自条目化。
2. **抽数据流**：
   - 前端 / 调用方状态：哪些字段、谁拥有。
   - 接口：方法 / 路径 / 入参 / 出参；PRD 没写的标 **【需澄清】**。
3. **列状态点**：loading / empty / error / success / 权限不足，各自的表现。
4. **列异常路径**：所有可能失败的环节 + 兜底策略。
5. **标复用候选**：在项目里查已有可复用的组件 / 状态 / 服务 / 工具，给出文件路径，无则写「未找到」。
6. **不写代码**，只产出结构化清单。

---

## 产出（Output）

一份结构化开发文档，含上述 5 个部分（功能边界 / 数据流 / 状态点 / 异常路径 / 复用候选）。

---

## 可直接粘贴的 Prompt

```text
你是当前项目的资深架构师。请阅读下面的 PRD，并按以下结构输出（不要写代码）：

1. 功能边界
   - 必须实现的核心能力（条目化）
   - 明确不在本期范围的能力（条目化）
2. 数据流
   - 状态：哪些字段、谁拥有
   - 接口：方法 / 路径 / 入参 / 出参（PRD 没写的标【需澄清】）
3. 状态点
   - loading / empty / error / success / 权限不足 各自的表现
4. 异常路径
   - 列出所有可能失败的环节及兜底策略
5. 复用候选
   - 查项目中已有可复用的：组件 / 状态 / 服务 / 工具函数
   - 给出文件路径，无则写"未找到"

PRD：
"""
<在这里粘贴 PRD>
"""
```

---

## 卡点信号（Stop signals）

- 输出里出现「大概」「可能」「应该是」→ PRD 不够清晰，停下要澄清。
- 找不到任何复用候选 → 多半没读够代码，先扩大检索范围。

---

## 自检清单（Self-check）

- [ ] 每个核心能力都有明确边界（做 / 不做）
- [ ] 接口入参出参完整，未知项已标【需澄清】
- [ ] 5 类状态点都覆盖
- [ ] 复用候选给了具体文件路径
- [ ] 全程没写代码
